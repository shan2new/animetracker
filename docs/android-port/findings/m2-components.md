# M2 audit findings (components, chrome, image pipeline, data layer) — 2026-09-04

Three adversarial critics. **Blockers and majors are remediated inside the workflow**; this is
the record of what they found, because several are the kind of defect a compiler can never see.


## Critic 1

**Verdict:** The design law's colour, chrome and composition rules hold; its "one of everything" rule does not. Nothing in the tree misuses amber — every `ThemeColor.accent` site is a fact, a state, or a ground with `onAccent` ink on it, and every bare tappable word resolves `LocalControlInk`. The chrome bars are correct in both branches (`ScrollEdgeChrome.kt:112-114`: `chromeBarOpacity` 0.74 over blur, `chromeBarOpacityOpaque` 1.0 only when `LocalCanUseMaterial` is false, resolved once as `SDK_INT >= 31 && !reduceTransparency` at `ChromeSurface.kt:125`); no bar can render transparent. There is one section-header family (`SectionHeaderRow`), one wide art card (`BannerCard`/`ProgressBanner` at `ThemeRadius.card`), one progress bar, one mark control, and no landscape frame fills a portrait cover — `BannerCard.kt:120`, `ProgressBanner.kt:81` and `ArtHeader.kt:95` all route `portraitSource` into the composite path. `Switch`, `AlertDialog` and `DropdownMenu` are each wrapped in `PreviouslyMaterialBridge` with every colour passed explicitly; no `Snackbar`, no FAB, no `TopAppBar`, no `MaterialTheme.*` read outside `Theme.kt`, and no prose restates a numeral or a bar. The failures are all duplication, and they cluster in three seams. The blocker is real and behavioural: `ui/art/Art.kt` runs a private second Coil pipeline, so every poster in the app is decoded and cached outside the bucket ladder and loses the no-flash probe, while two files' doc comments assert the opposite. Below it, the app has grown two button families (one with a name collision), three press languages with the sanctioned one unused by the components it names, two accessibility-size thresholds, and three different SF→Material glyph ratios — so a chevron in a `MediaRow` and a chevron in a `GroupedRow` are already different sizes on screen. Fix the pipeline first; then delete the duplicate button/press/threshold declarations in `ui/state/EmptyState.kt` and `ui/UiPrimitives.kt` in favour of `ui/control/Buttons.kt`, which is the file that documents itself as the owner.

## Critic 2

**Verdict:** The write policy itself is a faithful, careful port — all seven invariants hold in the audited files. One real defect (syncAmbient inside the write try-blocks) can make a membership/status write roll back after the server accepted it, one real CancellationException swallow exists in the data layer (AuthManager.signOut), and the trust layer is not yet wired at the app root, which currently makes cross-launch WriteIntent replay inert.

VERIFIED, point by point:

1. Progress never rolls back; membership/status do. Correct and complete. putProgress (AppModel.kt:1672-1691) records to SyncCenter and touches neither `localProgress` nor `library`; settleLocalProgress is called only on the success line, so a failed write keeps `settledAtSeq = null` and its overlay stays unconditional through reconcileLocalProgress until a server snapshot agrees with it — exactly iOS's expression of the rule. Rollback is present and index-accurate on all four account-fact paths: addToLibrary (pendingAdds removed, undo cleared only if it is still this add's), setStatus (withStatus(prevStatus), undo cleared only if `customMessage != null`), removeFromLibrary (re-insert at `min(idx ?: size, size)`, only if not already back), restoreRemoved (removed again, and deliberately records with `intent = null` so Discard is its only exit). The one exception is finding 1.

2. One PUT in flight per part, newest-wins, superseded dropped. Correct. ProgressLane (WritePolicy.kt:287-335) is a one-slot `queued` map plus a per-mediaId `lanes` job; `send` overwrites the slot and starts a drainer only when none is running; the drainer loops on `queued.remove(mediaId)`. 12→13→14 issues 12 then 14 and never sends 13. The CoroutineStart.LAZY / assign / start() sequence correctly defeats the Dispatchers.Main.immediate inline-execution race, and the `finally` is identity-checked so a torn-down lane cannot evict a freshly started one. `isQueued` reproduces iOS's `progressQueued[mediaId] == nil` guard exactly. The two lane bypasses (replay(Progress), and a stored retry closure calling putProgress directly) match iOS, where they are equally deliberate. ProgressLaneTest covers all six properties including "the in-flight write is never cancelled by a newer target".

3. CancellationException rethrown. One violation only, AuthManager.signOut (finding 2). AppModel's ten catch sites all rethrow; reload() and runSearch() correctly suppress the UI side-effect while still rethrowing, which is the right Kotlin translation of Swift's `guard !error.isCancellation`. ApiClient calls ensureActive() before anything else and correctly treats its own TimeoutCancellationException as a failure rather than a cancellation.

4. WriteIntent replay installed at start, cleared on teardown. Correct: AppModel.start() line 446, SyncCenter.teardown() sets `replay = null` and is reached from AppModel.teardown(). effectiveRetry() has no empty-lambda fallback, so a row with nothing runnable keeps its place rather than being cleared as if it had succeeded, and `intent ?: row.intent` on the update path preserves a restored row's only way back. See finding 4 for why this is inert until the root wires install().

5. Offline cache stamps a real savedAt and is deleted on teardown. Correct: reload() sets `lastLoadedAt = System.currentTimeMillis()` and passes that exact value to `cache.save`; start() adopts `lastLoadedAt = cached.savedAt` so the stale strip tells the truth; teardown() calls `cache.clear()`. See finding 5 for the temp-file race.

6. Every optimistic progress copy preserves `airings`. Correct, and structurally guaranteed: the only path is `Franchise.withUpdatedProgress` → `FranchisePart.withProgress` → `copy(progress = maxOf(0, episodes))`. A repo-wide grep finds no hand-built `FranchisePart(` outside its declaration. `Franchise.withStatus` likewise preserves `subscription.addedAt`.

7. Exactly one haptic per transaction. Correct on all eleven command paths. markThrough adds none of its own and relies on setProgress's; every undoAction passes `haptic = false`; undoTapped fires SELECTION on the action path and delegates to restoreRemoved/performUndo, each of which fires exactly one, on the others. The per-token floors (40 ms selection, 300 ms otherwise) and the per-token stamp array match iOS's 0.04/0.3 and per-token dictionary. Dead until FeedbackCoordinator.attach is wired (finding 4).

### [major] `AppModel.kt`

syncAmbient() sits INSIDE the success `try` of reload() (line 513), setStatus() (line 1497) and removeFromLibrary() (line 1528), so an ambient-layer throw is caught as an API failure. On iOS this is impossible — `EpisodeNotifications.sync` / `AiringLiveActivityManager.sync` are non-throwing Swift calls. On Android `AmbientSync.sync` is `suspend fun sync(...)` and CAN throw (the canonical case is SecurityException from AlarmManager once SCHEDULE_EXACT_ALARM is revoked at runtime; the interface's own KDoc in WritePolicy.kt:180 already says "It must not throw" but nothing enforces it). Consequences, all divergent from iOS: (a) reload() paints loadError = true ("Couldn't refresh") over a library that arrived and was already committed to `library`/`lastLoadedAt`/the disk cache; (b) setStatus() ROLLS BACK a status the server already accepted (`replaceFranchise(i, library[i].withStatus(prevStatus))`), clears the undo and files a bogus "Moved to X" failed change whose Retry re-issues a PATCH that already succeeded; (c) removeFromLibrary() RE-INSERTS a franchise the server already deleted and files a bogus "Remove from Library" failure. Fix: move `syncAmbient()` after the try/catch (or wrap it in its own guarded call) in all three, and in alertsWereAllowed() (line 631), which currently propagates the throw to its caller. This is the one place the audited write policy can violate its own rule set: it makes an already-committed membership/status write roll back for a reason that has nothing to do with the server.

### [major] `AuthManager.kt`

Line 413: `runCatching { Clerk.auth.signOut() }` wraps a SUSPEND call, so a CancellationException thrown while it is suspended is swallowed — the classic Kotlin structured-concurrency bug, and the only instance of it in the whole data layer. The file's own header (line 53) confirms `signOut` is an ordinary suspend function. After the swallow the coroutine keeps running: it calls `refreshClerkSignInState()` (a non-suspend fun that writes `_isSignedIn`) and returns a Boolean into an already-cancelled caller, which then acts on it (`sessionExpired()` at line 438 writes `_isSignedIn`/`_lastError` afterwards; Profile alerts on the returned value). Fix: `try { Clerk.auth.signOut() } catch (e: CancellationException) { throw e } catch (_: Throwable) { }` — the swallow of *ordinary* errors is deliberate and correct, only the cancellation case is wrong. Every other catch in the data layer is correct: AppModel.kt has ten catch sites and all rethrow (486, 514/526, 783/793, 831, 849, 1417, 1465, 1498, 1529, 1676), ApiClient.kt calls `currentCoroutineContext().ensureActive()` FIRST at 694/731 and correctly distinguishes its own TimeoutCancellationException, and every other `runCatching` (LibraryCache, RecentsStore, RewatchStore.persist/load, SyncCenter.persist/restore) wraps only blocking I/O or serialization with no suspension point inside.

### [major] `AndroidManifest.xml`

ACCESS_NETWORK_STATE is not declared, but SyncCenter.startMonitoring() depends on it — and depends on it UNGUARDED. SyncCenter.kt:201 does `isOnline = cm.activeNetwork != null` outside any runCatching, while its sibling `cm.registerDefaultNetworkCallback(cb)` on line 217 IS inside one. `ConnectivityManager.getActiveNetwork()` is @RequiresPermission(ACCESS_NETWORK_STATE) and throws SecurityException without it, so the asymmetric guard means the seeding read is the one that crashes. It only works today because the merged manifest picks the permission up transitively from a dependency (verified in app/build/intermediates/merged_manifest/.../AndroidManifest.xml, line 17) — a Clerk/AndroidX version bump that drops it silently breaks the app root. iOS's NWPathMonitor needs no entitlement, so there is no equivalent on that side. Fix: declare `<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />` in the app manifest and put line 201 inside the same runCatching as the registration.

### [major] `MainActivity.kt`

The trust layer is never wired, so two of the rules the audited files exist to enforce are currently inert. There is no call site anywhere in app/src/main for `SyncCenter.install(context)`, `SyncCenter.signals = { ... }`, `SyncCenter.startMonitoring(context)`, `RewatchStore.install(context)` or `FeedbackCoordinator.attach` / `InstallFeedback()` — MainActivity is still the M1 `Bootstrap()` placeholder. Concretely: without `install()` the `prefs` field stays null, so `persist()` returns at its first line and `restore()` never runs, which means **failed changes do NOT survive a relaunch and the entire WriteIntent replay path is dead** (SyncCenter.kt:459-500); without `signals` every `syncedLine()` reads "Not synced yet" and `isStale` is permanently false; and without `attach` `FeedbackCoordinator.fire` returns at `host?.get() ?: return` so no haptic ever fires. The code in the three audited files is correct — this is a wiring gap the root composable must close, flagged so it is not lost when the root lands.

### [minor] `LibraryCache.kt`

save() (line 82) launches on Dispatchers.IO and always writes to the same fixed temp path `library-cache.json.tmp`, so two overlapping saves genuinely interleave their `writeText` into one file and then rename the garbage into place — after which `load()` returns null and the "a launch with no network opens on the shows" guarantee is gone. reload() is re-entrant by design (start() launches one, sceneBecameActive() launches another, addToLibrary() awaits a third), so two successful reloads settling close together is reachable. iOS has no equivalent exposure: `Data.write(options: .atomic)` allocates a unique temp file per write, so concurrent writes each land atomically and the last one wins. Also `target.delete()` before `renameTo(target)` (lines 90-91) is unnecessary on POSIX and opens a window in which no cache file exists at all. Fix: unique temp name per write (e.g. `"$FILE_NAME.${System.nanoTime()}.tmp"`), or serialise saves through a single-threaded dispatcher/Mutex, and drop the pre-delete. RewatchStore.persist() (RewatchStore.kt:256-271) has the identical fixed-`.tmp` pattern on the same IO scope.

### [minor] `SyncCenter.kt`

retry() (line 393) and retryAll() (line 419) run `run(); settleRetry(key)` with no try/finally. `FailedChange.retry` is typed `suspend () -> Unit`, so a throwing closure both skips settleRetry — leaving `userRetriedAt[key]` stamped, which arms a spurious .directError haptic on the next unrelated background failure on that key within 30 s — and escapes into a SupervisorJob scope with no CoroutineExceptionHandler, i.e. the process default handler, i.e. a crash. iOS cannot express this: its `retry` is `@MainActor () async -> Void`, a non-throwing type. No closure the app registers today throws (all four AppModel retry lambdas either launch and return, or are putProgress, which catches Throwable), so this is latent — but it is the seam a future write is registered through. Fix: `try { run() } finally { settleRetry(key) }`, or catch Throwable around the call.

### [minor] `SyncCenter.kt`

Reachability flaps where NWPathMonitor does not. `onLost(network)` (line 209) sets `isOnline = false` unconditionally, and on a Wi-Fi-to-cellular handoff Android delivers onLost for the old default before onAvailable for the new one — so for that window `syncedLine()` reads "Couldn't check for changes" and every EmptyState/InlineNotice renders the offline copy, on a device that never actually lost connectivity. NWPathMonitor coalesces the handoff and keeps reporting .satisfied throughout, which is why iOS never shows this. Fix: on onLost, re-derive from `cm.activeNetwork` rather than asserting false (or debounce the false edge by a few hundred ms). Two smaller, benign deviations noted in passing, neither worth changing: SyncCenter.teardown() also resets `profileIsOpen` where iOS does not, and it omits the SeasonSweepLedger reset that iOS's SyncCenter.teardown() performs — on Android that is covered by `SessionResets.runAll()` in AppModel.teardown(), which is the only caller.


## Critic 3

**Verdict:** The chrome layer itself is faithful and safe: `canUseMaterial` is one boolean resolved once with a fail-safe `false` default, no blur/RenderEffect/Haze call escapes it (the single `Modifier.blur` in the module is SDK-gated with a designed pre-31 substitute), the hardened bar is exactly 0.74-over-blur / 1.0-opaque, the veil and mask stop tables and the bottom over-draw match the spec number for number, materials mount and unmount rather than sitting at alpha 0, and the scroll offset is quantised, de-duplicated and read only from draw lambdas and derivedStateOf. The image layer is where this fails. `ui/image/` is a correct implementation of spec §4 that nothing but the hero uses: every card, row, poster and episode tile goes through a second, parallel pipeline in `ui/art/Art.kt` that resolves against Coil's singleton loader — so the separate art OkHttp client, the memory/disk budgets, the bucket ladder, the per-bucket keys and the frame-one ladder probe are all inert, banners decode at full source resolution because Scale.FIT is never set, and the palette is `NoArtPalette` everywhere. Alongside that, the glass surfaces have the same split (`Modifier.chromeGlass` has zero call sites while Toast's `LocalChromeGlass` is never provided, so toasts and the sync banner are permanently opaque), and `ScrollOffset.past()` cannot fire for the billboard thresholds its own KDoc recommends, which would leave Today and Detail never hardening their bar. No bearer leak and no transparent-bar path exist — the leak risk is clean. Resolve the duplication (keep `ui/image/`, delete or reduce `ui/art/Art.kt` to its compositions), provide the two roots in MainActivity, unify the glass entry point, and give the boolean probes an unclamped offset before any screen work lands on top.

### [blocker] `Art.kt`

TWO PARALLEL ART PIPELINES; the audited one is unused. Every shipped art surface (PosterSlot, LandscapeArt, EpisodeArtwork, EpisodeStill, ArtBackdrop — consumed by ui/card/*.kt and ui/row/MediaRow.kt) calls Art.kt:210 `ArtImage`, which is a second implementation with its own GradientPlaceholder, SnapFitContentScale, BlurTransformation, fade constant and `LocalArtPalette`. Only hero/ArtHeader.kt imports com.anitrack.app.ui.image. Consequences, each one a spec §4.2-4.4 rule silently unimplemented on the surfaces that recycle hardest: (a) Art.kt calls `AsyncImage` with no `imageLoader` argument, so it resolves against Coil's SINGLETON loader — nothing in the module calls `artImageLoader()`, `artHttpClient()` or `SingletonImageLoader.setSafe`, so the separate art OkHttp client, the 25 %-heap memory cache and the 256 MB disk cache never apply, and art traffic goes out on Coil's default client; (b) no bucket ladder — `maxPixel` is passed raw to `.size()`, so §4.3's 'decode at the bucket, not the caller's request' is gone; (c) no `memoryCacheKey`, so Coil keeps ONE entry per URL and the 2048-px Detail hero and the 270-px Library row evict each other on every navigation — the exact coexistence bug ImageBuckets.key documents; (d) no `ladderHit`/`placeholderMemoryCacheKey`, so the frame-one no-flash guarantee is gone on recycled cells; (e) no `.scale(Scale.FIT)`, so coil-compose derives Scale.FILL from ContentScale.Crop and a square size box, and a 16:9 banner requested at maxPixel 1100 decodes at its full source resolution instead of ~1100 px on the long edge.

### [major] `ScrollOffset.kt`

THE 240-dp CLAMP MAKES THE DOCUMENTED HARDENING PROBE UNFIREABLE. `set()` clamps through `ThemeMetrics.scrollSample` (ceiling 240 dp) and `track(LazyListState)` pins the value at `saturatedOffsetDp` = 240 once the first item leaves, while `past()` (line 136) compares that clamped `y` against the threshold. The KDoc at line 128 explicitly instructs `val scrolledUnderBar by scroll.past(copyTop - band)`. For a billboard screen copyTop is ~heroHeight (0.68-0.72 x window, i.e. 570-620 dp) minus 16 minus the copy height, so the threshold lands around 300-500 dp of scroll — above the clamp, so `past()` can never return true and Detail/Today would never harden the bar or dock the title: content scrolls through the clock, the one defect this whole subsystem exists to prevent. iOS does not have this problem because it computes `under` from the RAW probe value and clamps only what feeds the veil (ios/Sources/Features/FranchiseDetail/FranchiseDetailView.swift:309-318: `let y = -minY; scroll.set(y); ... let under = y > copyTop - (topSafeInset + toolbarBand)`). Fix: give the boolean probes an unclamped channel, or drive them from the copy block's window position via onGloballyPositioned.

### [major] `ImageLoader.kt`

`ArtPaletteCache.tintOrNull` leaks in-flight entries on the exceptional path. ### [minor] `ImageLoader.kt`

### [minor] `ImageLoader.kt`

`artHttpClient(shared)` (line 269) adopts the API client's `Dispatcher` as well as its connection pool, described as 'the expensive, stateless parts'. A Dispatcher is not stateless: it owns the executor AND the maxRequests (64) / maxRequestsPerHost (5) budgets and the ready/running queues. A scroll burst of art fetches can therefore occupy the shared global budget and queue API calls behind image traffic — a shared timeout budget by another name, on the one axis the audit was checking. Timeouts, interceptors and the bearer are correctly separated. Suggest sharing only the connection pool, or giving the art client its own Dispatcher with an explicit maxRequests.

### [minor] `ArtHeader.kt`

### [minor] `ArtHeader.kt`
